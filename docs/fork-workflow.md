# Working on Event Horizon

Event Horizon is one branch, `engine-work`: upstream plus every addition. Changes are commits on it, and upstream
comes in by merge. `main` mirrors upstream and is never committed to.

## Changing the engine

### 1. Start from a current trunk

```sh
cd ~/src/horizon && git checkout engine-work && git pull --ff-only
```

### 2. Keep changes easy to merge

Every upstream merge goes through the files Event Horizon changes. The fewer lines it changes in upstream's files,
the fewer conflicts each sync has.

- Put a feature in a new module (`gfx/<feature>.rs`, `game/<feature>.rs`), with a few one-line hooks in the shared
  files. Don't edit the shared files in place more than you need to.
- Keep hooks additive, at the end of a list, block or match arm where you can. Don't reorder, reformat or rename
  upstream's code you aren't changing.
- Label each commit with its area (`lua: …`, `mob-ai: …`, `launcher: …`), so `git log --grep` finds a feature's
  history.
- Patch `third_party/` crates only as a last resort, in a commit of its own that names the upstream issue.

### 3. Rules from upstream that apply

Read upstream's [AGENTS.md](../AGENTS.md). Its rules on code apply here:

- Never commit Mojang's files or `.local/`.
- Run every game in scratch `HORIZON_HOME` folders.
- Put user-facing text through translations (`tr`, `lang::get`), never hard-coded English.
- Keep Horizon-only features off by default where they change the vanilla look.

Its rules on contributing (pull requests, claims, labels, release batches) are for upstream and don't apply.

### 4. Event Horizon's own rules

- **Both platforms.** Everything must compile on Linux (Vulkan) and macOS (Metal). Backend-specific code (`VK_*`
  extensions, HDR metadata, Anti-Lag) sits behind runtime checks or `#[cfg]`, and does nothing elsewhere.
- **A switchable feature** declares its switch in one file, `crates/horizon-client-render/registry/<id>.json`
  ([format](../crates/horizon-client-render/registry/README.md)). Options > Mods lists it. Never hard-code a
  feature's switch in the launcher.
- **Hook API numbers belong to upstream.** Upstream stamps its own (`@API:name@` placeholders,
  `tools/stamp_native_hooks.py`). An Event Horizon hook or helper is a pending fragment,
  `tools/native-hook-fragments/<name>.json`, whose doc comment says `API @API:<name>@`. `NATIVE_HOOKS_API` and
  `docs/native-mods.md`'s list stay upstream's. Lua and the modkit call hooks by name, so nothing needs the number.
- **Check names against upstream.** A hook or helper with the same name as one of upstream's stops the mod API
  generator. Prefer upstream's when it does the job.
- **Generated files are build outputs.** The typed mod API (`mod_api_generated*.rs`, `mod_api_host_generated.rs`)
  is generated by `horizon-mod-api-gen` during the build: never commit it. After a Lua API change, regenerate the
  checked-in references: `cargo run -p xtask -- hooks-doc` and `cargo run -p xtask -- lua-types`. Then copy
  `docs/api/horizon.d.lua` to the modkit's `types/horizon.d.lua`.
- **Lockfiles.** A new dependency of a crate the launcher also builds (`horizon-protocol`, `horizon-mods`,
  `horizon-theme`…) needs `launcher/Cargo.lock` refreshed in the same commit (`cd launcher && cargo metadata`).

### 5. Check it

```sh
cargo fmt --all
python3 tools/pr_ready.py --quick              # fmt, clippy -D warnings, the touched crates' tests
(cd launcher && cargo check)                   # only if you touched launcher/
cargo build --profile fast -p event-horizon -p horizon-client-lib
```

Then run the game once in a scratch `HORIZON_HOME` and use the feature. For a change the Lua mods can reach, run
`tools/fork-sync/game-checks.sh`. Before a push of a large change, run `tools/fork-sync/verify.sh`.

`python3 tools/pr_ready.py` without `--quick` also runs the parity harnesses your files affect, when the vanilla data
is in `.local/`.

### 6. Push

```sh
git push origin engine-work
```

On macOS, `tools/deploy_local_mac.sh` installs the build as a launcher version, marked with its commit. On Linux,
use the launcher's Versions page, **Import a game build…**.

## Syncing upstream

Sync when upstream has something Event Horizon wants: a fix, a new hook, a game update. Mod work never needs a sync.
The steps, the scripts and what to expect are in [tools/fork-sync/README.md](../tools/fork-sync/README.md).

In short:

1. `tools/fork-sync/merge-upstream.sh` tags the trunk, moves `main` to upstream and merges it.
2. Resolve what it lists, keeping upstream's structure and putting Event Horizon's change back on top of it.
3. Update `START_HERE.md`'s **Upstream base** line.
4. Run `verify.sh`, build, `game-checks.sh` and, on a Mac, `metal-launch.sh`.
5. `git push origin main engine-work`.

## Adding or dropping a feature

A feature is a set of commits on `engine-work`, plus its section in [fork-branches.md](fork-branches.md), the page
that says what Event Horizon adds and where. Add the section with the feature. To drop one, revert its commits
(`git log --grep '<area>:'` finds them), delete its section, and say in `START_HERE.md` what was dropped.
